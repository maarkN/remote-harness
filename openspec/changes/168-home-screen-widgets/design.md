## Context

`expo-widgets` already provides the iOS widget extension (`ExpoWidgetsTarget`) and the Live Activity of a session. It also supports Home Screen and Lock Screen widgets (`createWidget`, rendered from a JavaScript layout with `@expo/ui/swift-ui`, props kept in the App Group). Its Android side is a stub. Deny / Allow on the Live Activity are `LiveActivityIntent`s: iOS performs them in the app's process, the app's entry file answers them over a short-lived connection (`respondInBackground`). Widget buttons in `expo-widgets` are plain `AppIntent`s performed in the widget extension, where the app never hears about them.

## Goals / Non-Goals

**Goals:** glanceable counts, sessions and limits on the home screen (both platforms) and the iOS Lock Screen; one-tap Allow / Deny of the oldest pending permission with the app closed; data that follows the computer without the app open, without session content in any push.

**Non-Goals:** several computers in one widget (the widgets show the active computer); widget configuration (choosing a computer or a profile); questions and plans from the widget (they open the session); the offline history cache (#361).

## Decisions

- **One snapshot, two renderers.** `buildWidgetSnapshot` (pure, Vitest) turns sessions, pending requests, limits, the computer and the clock into `WidgetSnapshot`; both layouts only draw it. Order of the three sessions: a pending permission first (oldest request first), then waiting, then running, then the most recently updated; ended sessions never show. "Waiting" counts sessions in `waiting` or with a pending request. Usage limits show the highest percentage per window across the computer's profiles (the one about to block). Labels (translated with the app's i18n) and the theme palette travel inside the snapshot.
- **iOS: `createWidget` in the existing extension.** One widget kind, `SessionsWidget`, with `systemSmall`, `systemMedium`, `accessoryCircular`, `accessoryRectangular` and `accessoryInline`; the layout switches on `environment.widgetFamily`. Lock Screen families render without the theme background (vibrant mode). The gallery strings are string literals in the generated Swift, so `Localizable.strings` in the extension (per language, added by a config plugin) localizes them.
- **iOS buttons in the app's process.** The `expo-widgets` patch makes a widget `Button` whose target starts with `app:` use the Live Activity intent (`LiveActivityIntent`, performed by iOS in the app's process, also with the app closed) instead of the extension-only one. The app's existing interaction listener in the entry file strips `app:` and answers `allow:<id>` / `deny:<id>` like the Live Activity. Alternative considered: answering from the extension — rejected, it would need the Noise keys and the connection code in the extension.
- **Android: `react-native-android-widget`.** Widgets are React elements turned into RemoteViews by the library; `WIDGET_ADDED`/`UPDATE`/`RESIZED`/`CLICK` arrive in a headless task run by WorkManager, which is allowed to run with the app in the background (a plain service start from a widget broadcast is not, on Android 8+). Two widget names, `SessionsSmall` (2×2) and `SessionsMedium` (4×2). The last snapshot is kept in SecureStore (after first unlock, this device only) for the headless renders. Alternative considered: a Glance module of our own — rejected for now: much more native code for the same result.
- **Answering from a widget.** The tapped request disappears from the snapshot at once (optimistic, so a second tap cannot answer twice), the answer goes over a short-lived connection to the snapshot's computer, then a fresh snapshot is fetched over a short-lived connection (`sessions.list`, `permissions.list`) and published. If the answer fails, the refresh brings the request back.
- **Refresh push.** The daemon computes a signature of what widgets show (waiting and running counts, pending request IDs) after every session or permission change; when it changes it sends `{event: "widgets", daemonId}` as a data-only message to devices registered with `widgets: true`, at most once every 30 s per computer (a trailing send carries the latest change), never while an app is in the foreground (it publishes itself) and never with push off. iOS: background push (`content-available`, `apns-push-type: background`, priority 5); Android: data message with collapse key `widgets`. The app's background message handler (now on iOS too) fetches and publishes. Goes through the push relay unchanged (it forwards any message to the grant's token).
- **Publishing from the app.** A hook subscribes to the stores and publishes a debounced (1 s) snapshot while connected, and once more when the app goes to the background; with no paired computer it publishes the "pair" state, in the demo nothing.

## Risks / Trade-offs

- [iOS throttles background pushes] → the widget shows "updated N min ago" from the snapshot time, so stale data is visible; opening the app refreshes it.
- [LiveActivityIntent from a widget] → documented by Apple as performed in the app's process; same mechanism the Live Activity buttons already rely on.
- [Snapshot in the App Group (iOS) holds titles] → same as the Live Activity props; titles never go through push or a server.
- [A new native dependency on Android] → maintained, Expo config plugin, WorkManager-based; the version bump and a new build are needed anyway.
