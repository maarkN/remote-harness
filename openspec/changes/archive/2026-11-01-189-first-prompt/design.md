## Context

`LifecycleService.start` runs the profile launcher (a generated zsh script) with the agent's arguments (`--worktree`, `--model`, `--name`); the launcher opens the tmux window with `new-window … -e VAR=value "<command line>"`, the command line being the zsh `(q)`-quoted arguments joined by spaces, and the window's shell runs it. Prompts otherwise reach a session only through `InputService.sendText` (a tmux paste into a registered, controllable session). Codex fires `SessionStart` only with its first turn (see the codex-sessions spec), so a Codex session started from the app has no registered session to paste into until the user types something. See proposal.md for the motivation.

## Goals / Non-Goals

- Goals: one `session.start` carries the first prompt; the agent runs it as soon as it is ready, for Claude Code and Codex alike; line breaks and shell characters survive; nothing is pasted blind into a TUI that may not be ready.
- Non-goals: attachments on the first prompt (later, with #431 templates in New session); the demo daemon (it does not simulate `session.start`); Kimi CLI, whose CLI has no interactive-with-prompt flag.

## Decisions

- **The agent CLI's own initial-prompt argument, not a paste.** Every supported CLI takes an initial prompt and stays interactive (`claude [prompt]`, `codex [PROMPT]`, `gemini`/`qwen --prompt-interactive`), handles its own readiness (trust dialogs, startup), and then fires the usual hooks, so registration and the app's navigation need no change. Alternatives rejected: pasting after `SessionStart` (never happens for Codex before the first turn; for Claude Code it would race the TUI's startup) and pasting after a fixed delay into a bare pane (no readiness signal, and a Codex Enter within 120 ms of the paste becomes a newline). `--` precedes the positional prompt so a prompt starting with `-` or equal to a subcommand name is still a prompt.
- **`promptArgs` on the agent adapter**: the arguments placed before the prompt (`['--']`, `['--prompt-interactive']`), `null` when the CLI has none (Kimi CLI). The lifecycle service refuses a prompt for such an agent with `bad_request`, and the app hides the field for it (`canStartWithPrompt`, next to `canStartInWorktree`).
- **The prompt travels in the environment, not on the tmux command line.** The daemon sets `CLAUDE_REMOTE_PROMPT` in the launcher's environment; the launcher stashes it, unsets it (so a tmux server it may start does not inherit it), passes it to the window with `-e CLAUDE_REMOTE_PROMPT=…` and appends the literal ` -- "$CLAUDE_REMOTE_PROMPT"` to the command line, which the window's shell expands. Putting the text itself in the command line was rejected: zsh's `(q)` quoting turns a line break into `$'\n'`, which only zsh and bash read back (tmux runs the command with the user's default shell), and the whole `new-window` command must stay under tmux's 16 KB message limit. With a provider profile the window re-runs the launcher, which receives the expanded prompt in `$@` and passes it on with `exec`.
- **8 KB cap, checked by the daemon before launching** (`MAX_FIRST_PROMPT_BYTES`): the environment entry still rides in tmux's `new-window` message with everything else (cwd, name, the other variables), so the cap leaves room under 16 KB. The protocol only requires a non-empty string; the app maps `too_large` to a translated error. A first prompt is short by nature; longer text is sent once the session is open.
- **Log the fact, not the text**: `session started` gets `prompted: boolean`, in line with "prompts never go to the daemon log".

## Risks / Trade-offs

- [Codex named at start and given a prompt: `/rename <name>` is submitted when the session registers, which is now during the first turn] → Codex accepts slash commands in its composer; at worst the rename lands after the turn. Kept as is; the name is still applied as the title by the daemon.
- [The prompt is an argument of the agent process, visible in `ps` on the computer] → the same as `claude "prompt"` typed in a terminal, and as `--name` today; it is not on the tmux window's command line and not in the daemon log.
- [A launcher generated by an older daemon ignores `CLAUDE_REMOTE_PROMPT`] → launchers are rewritten by `install`, `setup` and after a daemon update; until then the session starts without the prompt, nothing worse.
- [A CLI changes its initial-prompt flag] → one line per adapter; the agents test pins the current flags.
