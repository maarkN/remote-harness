## Why

Starting a session and asking something takes two steps today: `session.start` opens the agent, then the user waits for the session to appear and types the prompt in the conversation (#430). The question is usually known when the session is created ("review this PR", "run the tests and fix"), so the New session screen can take it and the agent can run it as soon as it is ready.

## What Changes

- `session.start` accepts an optional `prompt`: the first prompt of the new session. The daemon checks it before launching (at most 8 KB, and only for agents whose CLI takes an initial prompt) and hands it to the agent CLI as its initial prompt (`claude … -- <prompt>`, `codex … -- <prompt>`, `gemini`/`qwen … --prompt-interactive <prompt>`), carried to the tmux window through its environment, never on the tmux command line. The CLI submits it itself when it is ready and stays interactive, so the session registers and turns `running` on its own. Without `prompt`, nothing changes.
- The New session screen shows an optional multi-line "First prompt" field under Name for profiles whose agent takes one; a non-blank value is sent as `prompt`, and the session opens already running.
- Works for Claude Code and Codex (and Gemini CLI, Qwen Code); Kimi CLI has no such flag, so the field is hidden for it and the daemon answers `bad_request`.

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `session-lifecycle`: "First prompt at start" (the `prompt` option, its limits and how it reaches the agent) and "First prompt field on the New session screen".
- `protocol`: "Message catalog" (`session.start` with an optional `prompt`).

## Impact

- `packages/protocol/src/client.ts` (`session.start` schema); daemon: `features/agents/{types,claude,codex,gemini,qwen,kimi}.ts` (`promptArgs`), `features/hooks/launcher.ts` (the prompt reaches the window through `CLAUDE_REMOTE_PROMPT`), `features/lifecycle/{service,index}.ts` (validation, launcher environment, log); app: `features/lifecycle/{NewSessionScreen.tsx,new-session.ts,start-plan.ts}`, i18n in pt-BR, en-US and es-ES; tests in `apps/daemon/test/{lifecycle,agents,hooks}.test.ts`, `packages/protocol/test/protocol.test.ts` and `apps/mobile/src/features/lifecycle/new-session.test.ts`.
- Launchers are regenerated by `remote-harness install`, by `setup` and after a daemon update; a launcher from an older daemon ignores the prompt variable and starts the session without the prompt.
- Older daemons ignore the unknown field (tolerant validation): the session starts without the prompt. The release notes say the daemon must be updated.
- No new dependency; no native change (ships over the air).
