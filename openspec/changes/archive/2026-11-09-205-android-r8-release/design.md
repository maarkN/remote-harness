## Context

See proposal.md for the motivation. The native Android project is generated (Continuous Native Generation): nothing under `android/` is committed, so every build setting goes through `app.config.ts`. The Expo template's `android/app/build.gradle` already wires `minifyEnabled` and `shrinkResources` to the Gradle properties `android.enableMinifyInReleaseBuilds` and `android.enableShrinkResourcesInReleaseBuilds`; `expo-build-properties` writes them to `gradle.properties` only when its options are set. React Native, expo-modules-core, react-native-firebase and reanimated ship their own consumer ProGuard rules, and the template's `proguard-rules.pro` keeps reanimated's worklets.

What the app reaches by name at run time, found by reading the local modules (`modules/hands-free-background`, `modules/voice-assistant`) and the config plugins:

- `HandsFreeService.smallIcon()` resolves `notification_icon` (drawable) with `Resources.getIdentifier`. The same drawable is referenced from the manifest (`expo-notifications`' default icon meta-data), and the resource shrinker's safe mode keeps resources whose names appear as string constants, so it would survive either way today.
- Nothing in the app's own code looks classes up by name: the foreground service, the assistant activity, the widget providers and the alternate-icon aliases are declared in the manifest, so AGP keeps them; the Expo modules are referenced from the generated module list and expo-modules-core's rules keep `Module` subclasses, records and enumerables. The local modules define no records.
- One library does, and the first R8 build caught it: `expo-task-manager`'s `TaskService` asks expo-modules-core's `AppLoaderProvider` for the headless app loader at every start, and the provider reads the class name (`expo.modules.adapters.react.apploader.RNHeadlessAppLoader`) from a manifest `<meta-data android:value>`, which neither AGP's manifest keep rules nor R8's constant-string tracking follow. R8 stripped the class (`usage.txt`), and the release build logged `ClassNotFoundException` at launch; a background task firing with the app closed (widget refresh push) would have found no loader. No Expo package ships a rule for it.

## Goals / Non-Goals

**Goals:**

- R8 shrinking, obfuscation and resource shrinking on every Android release build, including `make build-android-bundle` and `make install-android`.
- By-name resources kept explicitly, in one place, so a future refactor of the Kotlin side or a new by-name resource (#134) does not depend on the shrinker's heuristics.
- A local, device-free check that R8 compiles the app (no missing-class errors) before anyone tests on a phone.

**Non-Goals:**

- Shrinking the JavaScript bundle (Hermes bytecode is not touched by R8).
- Tuning R8 further (`proguard-android-optimize.txt` is what the template already uses; no custom optimization passes).
- Changing the iOS build.

## Decisions

- **Plugin options over a hand-edited `gradle.properties`.** The native project is regenerated by `prebuild --clean` on every store build, so the two flags live in the `expo-build-properties` block of `app.config.ts`. `enableProguardInReleaseBuilds` is the deprecated spelling (the plugin maps it with a warning); the current `enableMinifyInReleaseBuilds` is used.
- **An explicit `res/raw/keep.xml`, written by a `withDangerousMod` plugin from a `KEPT_ANDROID_RESOURCES` list.** Alternative: rely on the manifest reference and the shrinker's safe mode. Both hold today, but the keep file documents the contract next to the code that creates it and costs a few lines. The XML is produced by a pure function with a unit test; the plugin writes the file under `app/src/main/res/raw` of the generated project, the same way the voice assistant strings are written.
- **`extraProguardRules` for the headless app loader, in one exported constant.** `ANDROID_PROGUARD_RULES` keeps `expo.modules.apploader.**` (the provider, the interface and its `Params`) and every class implementing `HeadlessAppLoader`, which is how the manifest-registered loader is found. The interface-based rule rather than the class name, so another loader registered the same way is kept too. Any future rule goes into the same constant, never into the generated `proguard-rules.pro`.
- **Debug untouched.** The template applies the properties to the release build type only, so development builds keep their speed and readable stack traces.

## Risks / Trade-offs

- [R8 strips something only visible at run time] → nothing reflective was found, but the proof is a full pass on a release build on the Redmi 8 (Android floor) before the next bundle: navigation, deep links, pairing, push and live status, widgets, hands-free, voice assistant. Recorded as a manual item on #526.
- [Obfuscated crash traces] → the Crashlytics Gradle plugin uploads the mapping on release builds when `google-services.json` is present, and the `.aab` carries it for the Play Console. Check the first R8 build's traces in both.
- [Resource shrinking removes a resource looked up by name] → the keep file; any new `getIdentifier` call must add its resource to `KEPT_ANDROID_RESOURCES` (noted in CONTRIBUTING.md).
- [Smaller gain than expected] → the Hermes bundle dominates the download size; the Play Console score is DEX-only, which is what the issue measures.

## Migration Plan

Ships with the next Play bundle after 1.1.1 clears review, so a review outcome is never mixed with an R8 change. Rollback is setting the two options to `false` and rebuilding.
