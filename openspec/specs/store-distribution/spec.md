# store-distribution Specification

## Purpose
What the app stores need, kept in the repository: the listing texts and assets, the policy pages, the app identifier, the move from development builds and the instructions that let reviewers in without an account.

## Requirements

### Requirement: Store listing texts
The repository SHALL keep the store listing texts as a typed catalog in pt-BR, en-US and es-ES (`apps/mobile/store/metadata.ts`): name, subtitle, short description, full description, keywords, promotional text, release notes, support URL, marketing URL and privacy policy URL. The full description and the release notes SHALL have an App Store variant and a Google Play variant built from shared parts: Apple's guideline 2.3.10 forbids naming other mobile platforms in App Store metadata, so no App Store text names Android or Google, and no Google Play text names iPhone, iPad, iOS, Siri or the App Store. The three languages MUST have the same shape; the texts MUST respect the stores' limits (App Store name and subtitle 30 characters, keywords 100, promotional text 170, description 4000, release notes 500; Google Play title 30, short description 80, full description 4000, release notes 500); the URLs MUST be pages the site serves; the copy MUST be agent-neutral and name no private project. A script SHALL write the catalog in fastlane's `metadata/` layout for iOS and Android, each tree with its own store's variants.

#### Scenario: Limits
- **WHEN** a translation makes the subtitle longer than 30 characters
- **THEN** the test suite fails naming the language and the field

#### Scenario: Other platform named
- **WHEN** an App Store text names Android or a Google product, or a Google Play text names an Apple device or service
- **THEN** the test suite fails naming the language and the field

#### Scenario: fastlane tree
- **WHEN** the maintainer runs `pnpm --filter @remote-harness/mobile store:metadata`
- **THEN** `store/fastlane/metadata/ios/<locale>/*.txt` (App Store variants) and `store/fastlane/metadata/android/<locale>/*.txt` (Google Play variants) are written for the three languages

### Requirement: Store assets
The brand script SHALL produce, besides the 1024 app icon, a Google Play feature graphic of 1024 × 500 pixels with the mark, the name and the tagline, committed at `apps/mobile/store/feature-graphic.png` and regenerated by `pnpm --filter @remote-harness/mobile icons`.

#### Scenario: Regenerate
- **WHEN** the maintainer runs the icons script
- **THEN** the feature graphic is rewritten from the same source as the app icon

### Requirement: Store policy pages
The docs SHALL include a privacy policy page (`/docs/privacy/`, in the three languages) stating what the software collects, what stays on the devices, what leaves the machine and when, the permissions the app asks for and how to contact the maintainers; the landing footer SHALL link it. The support URL used in the listings SHALL be the troubleshooting page.

#### Scenario: Privacy URL
- **WHEN** a store form asks for the privacy policy URL
- **THEN** `https://remoteharness.app/docs/privacy/` answers with the policy in the visitor's language

### Requirement: Migration from development builds
The troubleshooting page SHALL tell users of the development-signed builds how to move to the store build: install it, pair again by scanning the code, let push re-register on first launch, delete the old build.

#### Scenario: Reader with a development build
- **WHEN** the TestFlight build becomes available
- **THEN** the docs explain why the new build starts empty and what to do

### Requirement: App identifier
The app SHALL use `com.alvyntech.remoteharness` as its iOS bundle identifier and its Android package, on both stores and in the builds made from the repository. The daemon's service label, the URL schemes, the notification channel and the data directory MUST NOT change with it. The docs SHALL tell users that builds with the former id (`tech.doctorx.clauderemote`) are a separate app that the new one does not replace.

#### Scenario: Build configuration
- **WHEN** the Expo config is resolved for iOS or Android
- **THEN** the bundle identifier and the package are `com.alvyntech.remoteharness`

#### Scenario: Phone with an older build
- **WHEN** a user with a `tech.doctorx.clauderemote` build installs the new one
- **THEN** both apps exist side by side and the troubleshooting page tells them to pair the new one and delete the old

### Requirement: Store review access
The repository SHALL keep, at `apps/mobile/store/app-access.md`, the instructions given to store reviewers in the "App access" declaration: the app has no accounts, and every feature can be reviewed with **Try the demo** on the pairing screen, without a computer, credentials or network. The declaration in the store consoles SHALL be copied from that file.

#### Scenario: Reviewer opens the app
- **WHEN** a reviewer follows the App access instructions
- **THEN** they reach the session list through **Try the demo** without any sign-in

### Requirement: Expo project slug
The app SHALL use `remote-harness` as its Expo project slug, matching the npm scope and the CLI name.

#### Scenario: Build configuration
- **WHEN** the Expo config is resolved
- **THEN** the slug is `remote-harness`

### Requirement: Store screenshots
The store screenshots SHALL be taken from the in-app offline demo, in pt-BR, en-US and es-ES, and MUST show only its fictional data: no real project, path, host name or conversation. A screenshot build, chosen at build time with `REMOTE_HARNESS_SCREENSHOTS=1`, SHALL put `screenshots: true` in the Expo config's `extra`; in that build the app SHALL open the offline demo by itself from the pairing screen once start-up has settled, and SHALL NOT render the demo banner nor the Settings Demo card, so the fictional computer passes for a paired one. Without the variable the config and the app MUST be unchanged, and a screenshot build MUST NOT be shipped. A script (`pnpm --filter @remote-harness/mobile store:screenshots`) SHALL drive an iOS simulator or an Android emulator through the storyboard scenes (session list, permission request, conversation, raw terminal, new session, settings) by deep link, set a clean status bar and the app's language per run, and save the raw captures under `apps/mobile/store/screenshots/<platform>/<locale>/`, which MUST be ignored by git; `--scenes`, `--locales`, `--name`, `--out` and `--wait` SHALL select a subset of scenes and languages, the file prefix, the folder and the timing.

#### Scenario: Screenshot build
- **WHEN** the app is built with `REMOTE_HARNESS_SCREENSHOTS=1` and opened on a simulator with no paired computer
- **THEN** the demo's session list appears by itself, without the demo banner, and Settings shows no Demo card

#### Scenario: Shipping build
- **WHEN** the app is built without the variable
- **THEN** `extra` has no `screenshots` key, the pairing screen waits for the user and the demo shows its banner

#### Scenario: Capture run
- **WHEN** the maintainer runs `store:screenshots` with `--android --apk <release apk>` against a booted emulator
- **THEN** `store/screenshots/android/<locale>/` holds one PNG per scene for each of the three languages

### Requirement: Android release build optimization
Android release builds (the Google Play bundle and the release APKs) SHALL run R8 with code shrinking, obfuscation and resource shrinking, configured through the Expo build properties so that the native project generated from the config carries `android.enableMinifyInReleaseBuilds=true` and `android.enableShrinkResourcesInReleaseBuilds=true`. Debug builds MUST stay unminified. Every resource the app resolves by name at run time MUST be listed in a resource keep file generated with the native project, so resource shrinking never removes it; today that list is the notification icon drawable the hands-free foreground service looks up. Any class R8 would otherwise strip although the app reaches it by reflection MUST be covered by a keep rule. Release builds SHALL produce the R8 mapping file, so Crashlytics and the Play Console show deobfuscated stack traces.

#### Scenario: Generated project
- **WHEN** `npx expo prebuild --platform android --clean` runs
- **THEN** `android/gradle.properties` has `android.enableMinifyInReleaseBuilds=true` and `android.enableShrinkResourcesInReleaseBuilds=true`, and `android/app/src/main/res/raw/keep.xml` keeps `@drawable/notification_icon`

#### Scenario: Release build
- **WHEN** the release variant is built from the generated project
- **THEN** R8 runs without a missing-class error, the build writes `mapping.txt` next to the outputs and the app's classes are obfuscated in the DEX

#### Scenario: Headless start on a release build
- **WHEN** a background task fires on a release build while the app has no activity (a widget refresh push)
- **THEN** Expo's headless app loader class is present and starts the app, with no ClassNotFoundException at launch

#### Scenario: Hands-free notification on a release build
- **WHEN** the hands-free foreground service posts its notification on a release build
- **THEN** the notification shows the app's notification icon, not the launcher icon fallback

#### Scenario: Debug build
- **WHEN** the debug variant is built
- **THEN** no minification or resource shrinking runs

#### Scenario: Play Console
- **WHEN** a bundle built this way is uploaded to the Play Console
- **THEN** the App bundle explorer no longer reports "Low" DEX code optimization
