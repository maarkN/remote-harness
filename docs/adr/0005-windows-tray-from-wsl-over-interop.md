# The Windows tray is C# compiled by PowerShell and started by the WSL daemon over interop

Under WSL the daemon has no desktop of its own, so its tray icon must live on the Windows host. We ship the helper as C# source (`apps/daemon/tray/windows/Tray.cs`) that the daemon starts through WSL interop as `powershell.exe -Command "Add-Type -Path …; [RemoteHarness.TrayApp]::Run()"`, talking the same JSON-lines menu protocol over stdin/stdout as the macOS and Linux helpers. Windows PowerShell 5.1 and .NET Framework (WinForms, GDI+, `JavaScriptSerializer`) are on every Windows 10/11 machine, so there is nothing to build in CI, sign against SmartScreen, download or install with `install.ps1`; the source updates with the daemon, like `Tray.swift`, and the code stays within C# 5 because that is what `Add-Type` compiles. Starting it from the daemon rather than from a Windows logon task reuses the existing helper lifecycle (an early exit leaves the daemon headless, the icon dies when stdin closes) and needs no socket between Windows and WSL; the logon task that already boots the distribution makes the icon appear at logon. We rejected a .NET/WinUI or Rust/Go binary installed by `install.ps1` and started at logon to attach to the daemon: it needs a build and signing pipeline, a Windows-side install and uninstall, and a new transport with reconnects, for the only benefit of showing an icon while the distribution is down. The cost is a dependency on interop and on PowerShell's execution policy (a machine forcing `AllSigned` gets no icon) and a second of compilation per daemon start.
