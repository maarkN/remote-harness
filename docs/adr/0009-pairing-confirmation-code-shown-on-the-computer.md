# A confirmation code shown on the computer completes every pairing

ADR-0002 made pairing codes single-use and short-lived, but the code still carries everything a device needs, including the secret that is the XXpsk3 PSK. Whoever sees the QR or the link within its 5 minutes (a screenshot in a chat, a terminal shared on a call, the output of `remote-harness pair` pasted somewhere) can pair before the owner does, and nothing on the computer asks for consent (#593). We decided that every pairing needs a second factor that never travels in the link: a 6-digit **confirmation code** the computer shows only once a device presents the pairing code, and that the user types on that device.

How it works. The app first *announces* the code: a connection whose preface has the new mode `0x03` and the pairing ID, and nothing else. The daemon generates the confirmation code for that pairing code (6 random digits, generated once and kept for the pairing code's lifetime), shows it, and closes the connection with 4011. The phone asks for the digits on its own screen and then pairs with the new preface mode `0x04`, running XXpsk3 with the PSK `HMAC-SHA256(secret, "remote-harness pairing confirmation" ‖ 0x00 ‖ digits)` instead of the secret. A wrong code fails when the daemon reads the third handshake message: it closes with 4012 and counts the attempt; the third wrong attempt burns the pairing code (4013) and logs a warning. The code expires with the pairing code (5 minutes from its creation). A passive observer of a pairing (the connection relay included) cannot test guesses offline, because the handshake keys also depend on the device's and the daemon's private keys, so guessing is limited to the 3 online attempts.

Where it is shown: only where the pairing code was shown, and only after a device presented it. `remote-harness pair` and the setup keep running after printing the QR and print "A device is pairing: enter 123 456 on it" (then that the device paired, or that the code was burned or expired); the tray's Pair a phone submenu and Pairing tab add the code under the QR; "Add device" on an already paired phone gets the code through `pairing.progress`, sent only to the connection that created the pairing code, and shows it in its sheet. A leaked link that someone else uses therefore shows up as an unexpected prompt on the owner's screen, and the confirmation code is never printed before a device asks, so a screenshot of the QR does not include it.

Compatibility. The link keeps `v=2`: bumping it would make older apps say only "Invalid QR". The daemon refuses the old pairing mode (`0x01`) with 4002, which older apps already show as "The app and the computer speak different versions. Update both." A new app that announces to an older daemon gets 4002 too (an unknown preface mode) and tells the user to update the computer. Reconnecting paired devices (mode `0x02`, IK) is unchanged, so updating either side never unpairs anything.

We rejected showing the confirmation code next to the QR when the code is created: simpler (no announce, the CLI exits at once), but a screenshot of the terminal or a shared screen would carry both. We rejected entering the code in the middle of one handshake (holding the socket open between the second and third messages while the user types): it needs long handshake timeouts on both sides and breaks when the phone locks or switches networks, where two short connections do not. We rejected letting the owner approve the pairing on the computer (a yes/no prompt): the CLI may already be closed and the tray has no prompt of its own, while typing a code proves the person holding the phone also sees the computer. The cost is one more step for every pairing and a `pair` command that waits until the phone pairs (Ctrl+C stops it).
